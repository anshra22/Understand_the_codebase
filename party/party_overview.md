# Parties Feature: Detailed Technical Overview

The "Parties" feature is the central CRM (Customer Relationship Management) and supplier database for the application. It acts as a foundational "Root Feature" (Phase 1 Master Data) that links real-world entities to all financial and inventory transactions.

---

### 1. The Core Data Model (`Party`)

The `Party` model (`lib/app/hive/models/parties.dart`) is comprehensive, containing over 32 fields. It serves as the primary source of truth for all entity information printed on documents like PDFs.

**Key Data Points:**
*   **Identity & Routing:** `partyId` (Unique ID for the entity), `businessId` (Links the party to a specific business profile).
*   **Categorization:** 
    *   `type`: Identifies if the entity is a `"customer"` or a `"supplier"`.
    *   `contactType`: Identifies tax registration status (e.g., `"unregistered"`, `"registered"`), which is critical for downstream GST/Tax calculations in the Sales feature.
*   **Names & Details:** `firstName`, `supplierBusinessName` (Firm name), `email`, `mobile`.
*   **The Address Block:** `addressLine1`, `city`, `state`, `zipCode`, `country`. (This data is pulled directly by the PDF generator to draw the "Billed To" / "Shipped To" sections of an invoice).
*   **Tax Information:** `taxNumber` (Stores the GSTIN or PAN).
*   **Financial State:** `balance` (Maintains a running total of the financial relationship—how much they owe you, or you owe them).

---

### 2. The Business Logic (`PartyAddFormController`)

The controller (`lib/app/feature/party/controller/party_add_form_controller.dart`) handles the creation and modification of Parties. Its logic goes beyond simple data entry; it actively participates in the application's accounting system.

**Key Discovery: The Opening Balance Dependency**
When saving or updating a Party, the controller checks if the user has defined an "Opening Balance" (e.g., "This customer already owes me $500 before using this app"). 

If an opening balance exists, the controller does not merely save a static `balance: 500` to the Party database. Instead, it actively generates a financial ledger entry:

1. It calculates whether the amount is a credit (`cr`) or debit (`dr`) based on whether the money is "To pay" or "To receive".
2. It constructs an `AccountLedger` object with the type `"opening_balance"`.
3. It borrows the `HivePosController` to inject this transaction directly into the `accounts_ledgers` Hive Box.

This ensures that the accounting system is perfectly balanced from the moment a customer or supplier is created.

---

### 3. Dependency Audit Summary

Based on our architectural methodology, here is the dependency profile of the Party feature:

*   **Reads from Global State:** `SharedPreferences` (Retrieves `userid` and `business_id` to generate a globally unique `partyId`).
*   **Reads from Master Data:** `Business` model (To associate the party with the current active business profile).
*   **Writes to Database:** `parties` Hive Box (The core save operation for the entity's profile).
*   **Writes to Database (Cross-Feature):** `accounts_ledgers` Hive Box (Injects foundational financial records if an opening balance is declared).
*   **Injects Controller (Cross-Feature):** `HivePosController` (Borrows logic from the POS system specifically to save the ledger entry securely).

---

### 4. Relevance to the Sales Invoice PDF Bug

If a bug on the Sales PDF involves the customer's Name, Address, GSTIN, or "Previous Balance / Due Amount", this overview identifies the exact source of that data:
1.  **Address/GSTIN/Name:** Sourced directly from the 32-field `Party` model created here.
2.  **Due Amount:** Sourced from the calculated sum of all `AccountLedger` entries tied to that `partyId`, the very first of which is the `opening_balance` ledger generated by this controller.
